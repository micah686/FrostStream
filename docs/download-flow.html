01 / The big picture

From a URL to a library item.

Three ways to request work. One shared pipeline that makes every item trackable.

01 / Ask

Describe what to save.

Submit a media URL, a playlist, or a channel. The API validates the request and resolves settings such as storage, cookies, priority and worker routing.

02 / Coordinate

Make trackable work.

DataBridge records the request and runs Cleipnir workflows. Collections become independent jobs, so each item has its own history and outcome.

03 / Preserve

Save more than bytes.

Workers acquire media and write files. The flow also stores metadata, links the library record and settles the result you see in the queue.

Accepted does not mean downloaded.

An HTTP 202 Accepted means the request was submitted. The queue shows the subsequent work. Likewise, yt-dlp finishing the transfer is only one stage: uploads, metadata, cleanup and finalization still follow.

Technical view · who owns what?
PartResponsibility
WebAPIValidate and submit requests; expose queue queries, history and live events.
DataBridge + CleipnirOrchestrate groups and item runs. Persist application state, attempts, warnings, leases and workflow progress.
Worker + yt-dlpDiscover media; fetch metadata; acquire and hash files; upload and delete artifacts.
Durable transportCarry commands and results. Full uses NATS JetStream; Lite uses a SQLite durable queue behind the shared interfaces.
Database + storageDatabase: searchable metadata and execution state. Storage backend: media and sidecar blobs selected by StorageKey.
Scheduler / background processorsTrigger creator scans and execute separately queued follow-up work such as audio renditions or chat ingestion.

02 / Single download

Follow one item, end to end.

Discover → check → acquire → store → catalogue → finalize.

Imagine saving one video. FrostStream first asks what it is and whether that source version is already in the library. If it needs new bytes, a worker downloads them into temporary storage. The flow then turns those bytes into a durable, catalogued library item.

Technical view · two different duplicate checks

Before downloading: compare the provider, source media ID and last-modified value with the stored source mapping. Equal last-modified values (including equal nulls) can return AlreadyDownloaded. ForceDownload bypasses this source-version shortcut.

After downloading: use the acquired file’s XXH128 content hash when reserving its media version. If that content is already stored, clean temporary files and link the existing media. Force does not turn off this content check.

The duplicate paths can still request an audio rendition when needed. A duplicate result is a useful terminal outcome, not an error.

Code reference: [01], [11]

Technical view · what has to be saved?
Artifact / operationPolicyWhy it matters
Primary mediaRequiredThe video or audio file itself; hash verification can check bytes during upload.

Optional does not mean every failure is harmless: interruption or Stop can abort the run and require compensation. A worker result of DownloadCompleted refers to media acquisition; the job is not finished until finalization.

Code reference: [01], [08], [10]

The finish line is a library item.

A successful finalization records Completed or CompletedWithWarnings. Audio rendition and enabled chat ingestion are queued separately afterward; their completion is not a prerequisite for the download’s terminal status. Metadata/search synchronization is requested during rich metadata writing.

03 / Playlist

One list becomes many journeys.

Expansion organizes the collection. Each child owns its own success or failure.

A playlist is an ordered list of items, so the first job is to discover that list. The group workflow gathers metadata pages, saves their entries, and creates a separate download request for each eligible item. Each child then follows the single-item pipeline above.

What a reader seesWhat happens underneath
A playlist starts expandingCreate or reuse its playlist row, then fetch flat metadata in pages of up to 5,000 entries.
Items appear in the queueAfter all pages are staged, evaluate title ignore rules. Record ignored entries; publish children for the others.
Some items finish; others failIndependent child flows allow siblings to keep working. Group totals summarize their outcomes.
A playlist item was already savedThe ordinary duplicate checks can reuse existing media and link it to the playlist.
Stop the playlistStop expansion and request Stop for existing children. Starting the group later starts its existing Stopped/Failed jobs; it does not resume an interrupted expansion.
Technical view · stable fan-out and settings

The group persists page results with Capture. It rejects a non-advancing next-page index. A child JobId is derived from playlistId + playlistIndex + entryUrl; its message ID is derived from groupId + jobId. These stable IDs support safe redelivery.

Each child inherits resolved storage, worker tag, yt-dlp options, cookies, priority, comments preference and the audio-rendition flag. It keeps the collection’s CorrelationId and has SourceKind.Playlist.

The direct-download endpoint recognizes playlist-container URLs and reroutes them. That route drops direct-only ForceDownload and tags because PlaylistRequested has no fields for them; there is a separate per-entry force-queue action.

The group publishes children through ordinary ingress. It deliberately avoids invoking a child inline or scheduling it as a lifecycle-dependent child of this short-lived coordinator.

Code reference: [02], [03], [04], [12]

04 / Creator / channel

Keep up with a changing source.

A one-off download gathers eligible items. Monitoring watches for new or changed ones.

A creator’s channel changes over time. FrostStream keeps a discovery catalogue so it can tell new or changed entries from entries it has already seen. A one-off channel download and an ongoing creator monitor use that same discovery machinery, with different selection rules.

PathEntry pointWhich items become jobs?
Download channelAPI creates/reuses source → Channel group → full scanQueueAllItems = true: all eligible candidates in this scan page, including unchanged ones. Each child still performs duplicate checks unless source-check force is requested.
Recurring creator monitorScheduler → full scan or incremental refreshNormally new or meaningfully changed candidates. Unchanged entries are updated in the discovery catalogue without another download request.
Scan nowManual scan endpoint → discovery directlyFull or incremental discovery using ordinary new/changed selection. This is a different action from Download channel.
Ignore rules stick.

For newly discovered items, a matching title rule records an ignored candidate and avoids enqueueing it. A creator item already marked Ignored remains ignored across later scans, including queue-all scans, until explicitly force-queued. Stopping a group suppresses new child requests while allowing discovery data to be saved.

Technical view · pagination, batching and group boundaries

Full scans use NextFullScanStartIndex (or 1) and examine at most 5,000 entries per source per invocation. Incremental scans start at 1 and clamp the configured page size to 1–500. Candidates are sent to DataBridge in batches of 100; an empty page still updates scan state.

DataBridge checks whether the group can accept children, resolves source config when appropriate, upserts discovery rows and publishes DownloadRequested for eligible candidates. Jobs are stable within the correlation/source/provider/extractor/media identity, while a later manual channel request can create fresh jobs under a new correlation.

A manual Channel group waits for an expansion success/failure/stop message and can retry retryable expansion failures. Scheduled scans and “Scan now” publish scan commands directly: they are not all wrapped in DownloadGroupV2Flow, even though the enum also defines CreatorMonitor.

Creator avatar/banner refresh is separate background work. It is not a prerequisite for every media download.

05 / Inside Cleipnir.Flows

The coordinator remembers.

Durable effects, message waits and immutable runs make the orchestration explicit.

Think of Cleipnir as a coordinator with a saved notebook. It records completed pieces of orchestration and waits for messages from workers. Workers perform the slow external operations; DataBridge decides which operation comes next and whether a reply still belongs to the current run.

One group flow

DownloadGroupV2Flow expands or routes a request. Its durable execution can end while children continue downloading. The group’s persisted aggregate is a separate concept.

One immutable item run

DownloadJobV2Flow owns exactly one run of one job. A user’s Start action creates a new RunId under the same JobId. It never restarts the old flow instance.

IdentityPlain languageTechnical purpose
CorrelationId / GroupIdThe batch this work belongs toConnect related items and group controls. Group instance: {groupId:N}.
JobIdThe item’s tracking recordStable across user-created reruns of that job.
RunIdThis particular try at the whole downloadJob flow instance: {jobId:N}-{runId:N}.
Stage + Attempt + DispatchIdThis operation, this attemptDistinguish retries and reject replies for an old dispatch. ArtifactKey distinguishes individual sidecars.
MessageId / OperationKeyThe envelope and logical operationMessage processing and Cleipnir mailbox idempotency help prevent duplicate advancement.
Technical view · Capture, Messages and the two ledgers

Capture(...) is used around configuration resolution, generated IDs, repository operations, command publication and retry waits. Cleipnir persists completed effects/results so workflow re-entry can use recorded results. This is not a blanket guarantee that an external operation happens exactly once: message IDs, database checks and execution leases also protect the boundaries.

Messages.OfTypes<Success, Failure>().First() waits for a stage result. The invocation can suspend while waiting. The event consumer checks the authoritative current execution, releases its lease, records history, then calls flows.SendMessage(instance, event, idempotencyKey: OperationKey). Stale or duplicate results are acknowledged without advancing the run.

Workflow store: parameters, effects, ordered messages, execution state and related runtime records. Application store: jobs, immutable runs, stage attempts, artifacts, warnings, leases, groups and library data. Queue state is driven by the application records.

Full uses PostgreSQL workflow persistence; Lite uses SqliteFunctionStore. The pinned Cleipnir packages are 4.2.5. Automatic flow registration and NodaTimeFlowSerializer are configured in DataBridge so persisted timestamps retain their meaning.

Code reference: [01], [06], [09], [18], [19], [20], [25]

Durable waiting is not automatic restart recovery.

Within a running DataBridge generation, the flow can wait and continue from recorded progress. On a DataBridge restart, FrostStream deliberately invalidates unfinished download workflows. The policy below takes precedence over the workflow engine’s general recovery capability.

06 / Failures & control

What happens off the happy path?

Retries, warnings, Stop and interruption each have a different meaning.

A slow network, a missing optional thumbnail, a user pressing Stop and a worker disappearing are different events. FrostStream records those differences instead of treating every problem as another download retry.

SituationImplemented behaviorWhat happens next
Transient / timeout / unknown failureUp to 3 stage attempts, separated by a 5-second retry delay. Collection expansion has the same attempt/delay limits.Retry the stage. Exhausted required work fails; optional work can warn.
Provider blocks downloadsThe metadata/acquire failure can open a provider circuit and fail the run. New matching work is prevented from starting.Clear the circuit before starting affected jobs again.
User presses StopQueued work can stop immediately. Active work gets a stop signal; the worker cancels and stage boundaries settle the run. Uploaded work may need compensation.Stopped after settlement, or Failed if cleanup is incomplete.
Worker stops heartbeatingExecution lease lasts 45 seconds; worker renewal interval is 15 seconds. A monitor checks every 5 seconds. Expired leases fail the run and delete its flow instance.Manual Start creates a fresh run. Uncertain uploads are marked Residual; deletion is not assumed.
Required artifact / metadata failureAttempt to delete recorded artifacts, temporary files, the reserved version and newly created media identity as appropriate.Failed, or Stopped if Stop was requested. Incomplete compensation records residual warnings and compensation_incomplete.
Optional artifact or ordinary temp cleanup failureRecord a warning after allowed retries and continue when the failure is not a run-level interruption.Successful finalization may become CompletedWithWarnings.

When DataBridge restarts

The startup gate runs before download consumers become ready. It deletes unfinished item flow instances and group flow instances, reconciles records, expires leases and establishes a new generation boundary.

Before restartAfter reconciliation
Queued job / runStopped — service_restarted_before_start.
Running, Stopping or Compensating job / runFailed / Interrupted — service_restarted.
Active groupMarked failed during reconciliation; child aggregate updates may refine the displayed group outcome.
Old queued request arrives after startupGeneration checks prevent silent auto-start of old work.
User selects StartA Stopped/Failed job receives a new RunId and begins the pipeline again. Existing history stays available.
Technical view · Stop, leases and honest cleanup guarantees

Stop is both a persisted decision and a signal. DataBridge sends a message to the exact run and publishes a worker-cancellation signal. A command dispatched just before Stop can acquire a lease marked stop-requested and immediately cancel, allowing the waiting flow to receive a terminal reply.

Lease expiry takes a different route: the monitor fails the run and deletes its workflow. An upload may already have reached storage, so records of uncertain uploads become Residual. Neither this interruption path nor startup reconciliation promises to execute the normal in-flow compensation sequence.

The monitor also checks older active runs for a missing or terminal Cleipnir instance and turns that inconsistency into an explicit failure rather than leaving the job Running forever.

Start group visits existing Stopped/Failed child jobs. It does not create a new expansion coordinator or rediscover items that were never fanned out; submit the collection again when you need another expansion.

    08 / Reading the queue

    Understand the outcome.

    A progress bar describes activity. The final state describes the result.

    The queue is your view into the application’s records. Live progress helps explain what the worker is doing, while terminal status tells you what the complete workflow achieved.

    TermMeaning
    Queued / RunningWaiting to begin / actively executing a run. WaitingForWorker and RetryWaiting describe more precise stage conditions.
    CompletedRequired download work and finalization succeeded.
    CompletedWithWarningsThe download finished, with recorded issues such as missing optional artifacts or incomplete temporary-file cleanup.
    AlreadyDownloadedAn existing source version or stored content was reused.
    IgnoredAn entry was deliberately excluded by a rule; it was not downloaded by that request.
    Stopping / CompensatingCancellation or rollback is still being settled. These are not final success states.
    Stopped / FailedThis run ended without successful finalization. Start can create a fresh run when allowed.
    Group CompletedWithFailuresThe collection has child failures. This does not erase successful siblings.
    Technical view · progress is advisory, state is authoritative

    The Worker publishes DownloadProgress frames over the live message bus. The API’s DownloadQueueHub forwards them through Server-Sent Events (SSE), with per-job coalescing. The queue controller also exposes queries for snapshots, detail and history.

    Live streams have no replay and do not automatically close when a job finishes. DataBridge separately persists throttled progress log lines for later inspection. A percentage or yt-dlp “finished” message does not itself advance the durable flow; validated result events and repository transitions do.

    Code reference: [08], [09], [21], [22]

    A short glossary

    WordIn everyday language
    FlowA saved program that coordinates a process and can wait for messages.
    Fan-outTurn one collection request into many independent item requests.
    SidecarA companion file such as metadata, captions, a thumbnail or chat replay.
    LeaseA time-limited claim that a particular worker is handling an operation.
    IdempotencyMake receiving the same logical request again safe to handle.
    CompensationExplicitly undo effects of an incomplete operation, such as deleting uploaded files.
    Residual artifactA file that may still exist after interrupted or unsuccessful cleanup.
    Provider circuitA persistent block on starting downloads from a provider that has rejected access.
