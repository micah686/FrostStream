# Phase 2a — persistence boundaries and SQLite baseline

Status: 2a–2c complete; 2d–2f pending. Audited against repository sources on 2026-10-03. The 2a increment changed documentation/inventory only. The 2b foundation now supports opt-in SQLite initialization; 2c now provides core repository adapters; normal runtime still uses PostgreSQL pending 2d–2f. Lite persistence is not complete.

The [generated inventory](phase2-persistence-inventory.md) links every shared entity declaration, EF configuration, persistence contract, observed runtime SQL dependency, and migration version. The [implementation checklist](phase2-checklist.md) orders the remaining work. Source inspection verifies the inventory. In 2b, disposable PostgreSQL catalog capture and SQLite foundation tests verified schema coverage; 2c verifies shared core repository cases on real PostgreSQL and SQLite. Bulk/contention, workflow durability and restart closure remain pending.

## Current ownership and persistence paths

[DataBridgeModule](../src/App/DataBridge/DataBridgeModule.cs) delegates database composition to [PersistenceRegistration](../src/App/DataBridge/Persistence/PersistenceRegistration.cs). The PostgreSQL pass registers `DataBridgeDbContext` with `UseNpgsql`, NodaTime and snake case naming, a separate raw `NpgsqlDataSource`, and FluentMigrator's PostgreSQL runner. Full runtime retains Cleipnir's PostgreSQL store. `InitializeDataBridge` runs `MigrateUp` before hosted services start. Both [DataBridge](../src/App/DataBridge/Program.cs) and [Lite](../src/App/Lite/Program.cs) use that initialization path. Lite's initialization-only option composes just the selected database; normal runtime composes the same application modules and remains PostgreSQL. Switching EF alone would leave the raw data source, migrations and workflows on PostgreSQL.

Shared entity classes live in `Shared/Database`; `DataBridge/Data/*Configuration.cs` supplies their EF mappings. The 45 DbSets cover storage and its protocol-specific child tables; download jobs, groups, runs, attempts, artifacts, leases, warnings, history, progress and message deduplication; media identities/versions and rendition status; local imports and import sessions; playlists and memberships; presets/configuration; schedules; discovery sources and scan state; users, cookies and notes. Entity and table names differ in places, e.g. `MediaEncodingStatusEntity` maps to `media.audio_encoding_status`.

EF is not the whole database model. The metadata tables (accounts/external IDs, captured media metadata, technical streams/chapters, captions/comments, series/music, taxonomy and junctions), watch/like state, access policies and their child tables, provider circuits, statistics and maintenance policies also have raw-SQL persistence. Their DDL is in FluentMigrator; their DTOs are shared, but many have no EF entity. A baseline made only with `EnsureCreated` or the DbSets would omit required tables, constraints, indexes and seed rows.

Repository contracts and read service interfaces remain shared (see inventory). `MetadataRepository` casts EF's connection and transaction to Npgsql and writes the whole captured metadata graph in one transaction. `UserNotesRepository` has an Npgsql-specific relational search branch. SQL read services include metadata, account/caption/thumbnail reads, rendition queues, encoding status, statistics and `MediaDocumentQuery` for search hydration. `MediaStreamReadService` uses shared persistence through EF and related services.

Several consumers execute SQL themselves: watch/likes, access policy execution, media deletion, background cleanup and statistics recording. Preserve their handlers/business decisions; extract database operations before enabling SQLite. Storage CRUD, sessions, preferences, cookie profiles and owner seeding also access EF directly and require the same portable mappings even where they do not own SQL.

Optional live chat uses ClickHouse for replay data and the selected application database for media markers/backfill selection. 2c adapts the latter and Typesense hydration queries; ClickHouse schema/ingest and the external Typesense store stay separate. NATS/JetStream durable queues, sessions and import object storage are Phase 3, OpenBao secrets and backups are later scope. They must not be mistaken for SQLite application tables to add in 2b.

## PostgreSQL features and required translations

| Feature actually used | Evidence and semantics to preserve | SQLite decision |
| --- | --- | --- |
| Schemas and native enums | `PostgresModelConfiguration` declares 23 PostgreSQL enums, repeated in `PostgresPersistenceRegistration`; metadata availability/subtitle enums exist only in raw SQL/migrations. M075 moves jobs tables/types from downloads/playlists into jobs. | Flatten names to `schema_table` (e.g. `jobs_download_jobs`, `media_media`), with a central name map used by DDL, EF and SQL. Store native enums as stable PostgreSQL labels in TEXT with CHECK constraints; retain existing explicit string conversions. Do not persist ordinal CLR values or infer labels by `ToString`. |
| JSON | `jsonb` holds yt-dlp options, ignore keywords, import metadata/sidecars, preferences, attempt payloads and worker lease payloads. Metadata/search use ordered `json_agg`/`row_to_json`. | Store JSON as TEXT with identical serializers/null semantics and EF value comparison where needed. Read child rows in deterministic order and assemble shared DTOs instead of relying on PostgreSQL aggregate syntax. Validate JSON at write boundaries; choose any schema JSON validation only after checking the deployed SQLite capabilities. |
| Arrays | `ANY(@ids/@statuses/@groups)` in purgers, deletion, policies and search; policy source lookup uses `array_agg` and `ARRAY[]::text[]`. No PostgreSQL array column declaration was found in the application migrations. | 2c binds JSON arrays into SQLite `json_each` membership queries, including empty arrays, using one parameter. This supersedes the proposed expanded IN lists and avoids the parameter-count limit. PostgreSQL retains native arrays; SQLite JSON aggregates decode to collections. Preserve distinct/order/case normalization. Array parameters and aggregate results are separate from JSON-backed collections. |
| Time/date | EF uses NodaTime `Instant` with `timestamp with time zone`; raw reader helpers normalize DateTime to UTC. M006 uses `AsDateTime` for metadata/comment dates, which must be audited separately from timestamptz. Statistics uses UTC `LocalDate`; seed schedules use `now`, `date_trunc` and intervals. | Use signed INTEGER Unix microseconds for persisted Instants (including nullable values) and invariant ISO date TEXT for calendar dates. Normalize raw metadata timestamps to the current UTC interpretation. Preserve PostgreSQL microsecond precision; make comparisons/order SQL numeric. Use the shared clock for new writes and scheduling seeds, with explicitly translated defaults for database-generated timestamps. Test pre-epoch, null and precision boundaries. |
| IDs, booleans, generated keys | UUID media/job/run IDs, generated numeric metadata IDs, booleans and RETURNING in metadata upserts. | Use normalized lowercase 32-hex GUID TEXT consistently in EF and raw SQL, INTEGER booleans with checks, and INTEGER generated keys. Preserve uniqueness, nullable unique-key behavior and returned identity semantics. |
| Query dialect | `::enum/uuid/text`, `ILIKE`, `DISTINCT ON`, regex `~`, ordered JSON aggregates, FILTER aggregates and schema-qualified references. | Explicit provider queries, no global string replacement. Use deterministic latest-row/window or correlated selection; assemble aggregates portably. Define and test search case/escape behavior rather than assuming SQLite LIKE equals PostgreSQL ILIKE. Parse workflow instance IDs in shared code. |
| Upserts | Metadata account/taxonomy/external-ID upserts, processed-message deduplication, group creation, provider circuits, watch/likes and statistics increments. | Preserve conflict targets, COALESCE rules, atomic increments and affected-row/RETURNING behavior in operation adapters. Read-then-insert without a transaction is not equivalent. Verify SQLite engine support before depending on RETURNING. |
| Bulk/set operations | Import inserts in batches of 500; discovery batch upserts; EF ExecuteUpdate; playlist reorder; metadata child replacement; purgers in batches of 500. No application COPY/binary-import/NpgsqlBatch path was found. | Keep behavioral batching; bound parameter counts and transaction duration. Review all rows touched by a logical operation, not only methods named Bulk. Complete contention work in 2d. |
| Locks and transactions | `DownloadFlowV2Repository.LockJobAsync` uses SELECT FOR UPDATE inside EF transactions; metadata uses the EF transaction in raw commands; playlist reorder and deletion/purge operations have multi-statement transactions. No explicit runtime SKIP LOCKED/advisory lock/isolation override was found in DataBridge. | Retain operation-level atomicity. PostgreSQL keeps row locks; SQLite acquires a write transaction before reading state for mutation, with bounded busy handling and whole-operation retries where safe. Share the EF connection/transaction with raw commands. A connection factory alone cannot provide row-lock equivalence. |
| Unbounded operations | Purger and background cleanup commands set CommandTimeout to zero. | SQLite adapters need finite busy/retry budgets, cancellation and short batches; do not copy unlimited timeout assumptions. Avoid network, filesystem or message dispatch while holding a writer transaction. |

These were design choices at 2a. The 2b foundation installs provider type mappings, schema, connection setup and initialization; 2c adds operation-specific SQL and shared parameter/reader/error adapters. No portable SQL equivalent is assumed for PostgreSQL schemas/native enum DDL, row locks, array parameters, regex UUID casts or Cleipnir's PostgreSQL DDL. Their implementations remain provider-specific. Ordinary LINQ queries, shared models, workflow decisions, serializers, ownership rules and repository method contracts stay shared.

## Smallest adapter boundaries

Provider composition, model mappings and core operation adapters are implemented under `DataBridge/Persistence`; mutation/retention/store work remains in 2d–2f. Select provider once at composition/startup using deployment mode and the explicit 2b opt-in; do not sprinkle mode checks into repositories or consumers. Keep the PostgreSQL defaults and registration behavior until SQLite is verified.

1. **Provider registration and migration boundary.** One registration entry point configures the EF provider, raw connection creation, name/type mapping and migration runner. An application migration initializer selects exactly one history before consumers/flows start. Full's PostgreSQL migration scan must never include SQLite-only migrations. The SQLite connection factory configures foreign keys, WAL and bounded busy handling on all relevant connections, including workflow connections.
2. **Provider model configuration.** Extract shared keys, relationships and indexes from provider column types/default SQL. Apply only the selected provider's mappings. Avoid indiscriminate assembly scanning once separate PostgreSQL/SQLite configuration classes exist. If both models use the same DbContext type, include provider identity in EF model caching when necessary. This keeps ordinary EF repositories and contracts intact.
3. **Database operation adapter.** Introduce operation-focused contracts for the existing raw SQL: metadata graph read/write, watch/like state, policies, deletion/retention, statistics, provider circuits, message deduplication and search hydration. Use existing read/repository interfaces wherever they already cover the operation; add narrow internal contracts for SQL currently embedded in consumers. Shared code constructs the operation and interprets results; provider code owns table names, SQL, parameter binding and reader conversion. Do not duplicate whole repositories to translate a few queries and do not introduce a universal SQL dialect parser.
4. **Atomic state mutation boundary.** A transaction runner owns the shared connection/transaction and executes database-only callbacks. A download mutation operation combines job read, run/attempt/lease checks and writes under the provider's locking discipline. Keep stale RunId/AttemptId checks and existing transitions in shared code. SQLite uses serialized writer transactions; PostgreSQL retains FOR UPDATE. Retry only complete idempotent operations on classified contention errors, never an arbitrary fragment or a callback that already published a message.
5. **Workflow store and retention boundary.** Cleipnir's store contract is the durability boundary; retain shared flows and `NodaTimeFlowSerializer`. Add a terminal-instance query abstraction used by both purgers so business retention code no longer queries `cleipnir.flows`. Delete instances through Cleipnir control panels to keep dependent state consistent. Confirm the exact pinned store interfaces in 2e before implementing them; an in-memory store is not an acceptable Lite fallback.

## 2c implementation evidence

[ApplicationDatabase](../src/App/DataBridge/Persistence/ApplicationDatabase.cs) owns the selected raw connection/command boundary. [Query families](../src/App/DataBridge/Persistence/Queries/README.md) contain 141 explicit PostgreSQL/SQLite statement pairs, with PostgreSQL text retained verbatim. Shared EF/raw parameter and reader codecs reuse 2b's encodings. Connection-local search/UUID/epoch functions provide SQLite expressions while Full uses native PostgreSQL expressions. `ApplicationDatabaseErrors` classifies unique conflicts without masking FK/check errors.

Fifteen behavioral cases run on both real providers, plus a SQLite catalog preparation test. Ordinary metadata, policy, playlist and content transactions work through the adapters; media/policy deletion explicitly shares a transaction. SQLite omits row-lock clauses inside the existing immediate writer transaction, but the broader atomic mutation contract, pre-transaction reads, busy retries, bulk and racing-writer proof remain 2d. Both workflow-aware purgers depend on 2d/2e. Normal Lite SQLite runtime remains gated through 2f.

## Cleipnir and restart behavior

The effective central package file is [src/Directory.Packages.props](../src/Directory.Packages.props), imported by the root package file. `Cleipnir.Flows` and `Cleipnir.Flows.PostgresSql` are pinned to **4.2.5**. Registration uses `UsePostgresStore`, automatic flow registration, `NodaTimeFlowSerializer` and graceful shutdown. M004 creates only the `cleipnir` schema; the library creates/upgrades runtime tables using a connection with `Search Path=cleipnir,public`.

The application explicitly references `cleipnir.flows`, and deletion comments identify `flows_effects`, `flows_messages` and `flows_timeouts`. Treat these as observed dependencies, not a complete store contract. In 2e inspect pinned 4.2.5's transitive ResilientFunctions store interfaces and initialization/versioning behavior; inventory all required state, leases/epochs, scheduling/timeouts, messages/effects and recovery data from that contract. Library DDL is not covered by the 97 FluentMigrator migrations.

`DownloadHistoryPurger` and `ImportSessionPurger` identify terminal/orphan flows with PostgreSQL status arrays, instance regex/substring UUID casts and joins to owning rows; actual deletion uses control panels. This coupling must move behind the retention boundary even if EF repositories already pass on SQLite.

`DownloadFlowStartupService` is already a blocking Full startup gate: it deletes non-terminal run flow instances and group instances, calls `ReconcileForStartupAsync`, and sets a generation timestamp before later consumers start. The repository stops queued jobs, fails active work and expires leases; ingress/results use immutable run identities to reject stale work. Therefore 2f ports and verifies existing reconciliation rather than inventing a new generic auto-resume rule. Import workflow recovery is a separate durable-store test. Durable-store recovery must work even though download startup intentionally invalidates unfinished runs.

## Migration history and baseline choice

The inventory verifies **97 consecutive source migrations, versions 1–97**. It does not assert that every deployment has applied them. Full uses FluentMigrator's existing version tracking; there is no EF migration sequence to rewrite. Important landmarks:

- 1–4: storage, secret removal, initial download tables, Cleipnir schema.
- 5–14: media identities/metadata, playlists, presets, schedules and discovery.
- 15–62: orchestration, storage/import configuration, users/notes/playlists, watch/likes, rendition and access changes. Several now-removed features appear in this history.
- 63: download V2 groups/runs/attempts/artifacts/leases/warnings/circuits and enum extensions; 64–72: import/access/storage changes and removal of legacy maintenance features.
- 73–80: durable statistics, schedule names, move orchestration into jobs, split playlist/source metadata and creator scan state, account linkage and library metadata detachment.
- 81–97: retention/seeds, audio status, configuration changes, indexes, removal of the legacy flow reset, channel download ledger, network storage, live chat marker and stage.

M005, M032, M040, M042, M063 and M097 use `TransactionBehavior.None`, including enum additions. M075's schema/type moves, destructive removals and PostgreSQL schedule seed expressions make replaying this history against SQLite unsuitable.

**Decision: a separate, checked-in SQLite baseline version 1 representing the final application schema through PostgreSQL M097.** Maintain a dedicated SQLite application migration version table and runner. Include all currently required raw-SQL tables, FKs, constraints, indexes and active seeds in addition to EF entities; exclude removed legacy features. Flatten schema names and apply the type choices above. Reserve `cleipnir_` names for the independent workflow store's schema initialization in 2e. Do not set Full's version table to 97 in SQLite or pretend SQLite has replayed PostgreSQL history.

In 2b derive a table/column/FK/index/seed manifest from a disposable PostgreSQL database after MigrateUp through 97, then compare it against EF and every raw query in the inventory. This catches drift and deleted/renamed tables that cannot be inferred from a list of Create.Table calls. Check in the normalized manifest alongside the SQLite baseline and run fresh initialization twice. The source cutoff and final catalog were captured and verified in 2b; see the [baseline README](../src/App/DataBridge/Persistence/Sqlite/Schema/README.md). PostgreSQL-to-SQLite data conversion is deferred by SIDE_PLAN.MD.

After the baseline, shared change descriptions should express portable additions/constraints where practical; provider-specific migration bodies handle SQLite table rebuilds and PostgreSQL enum/schema operations. Histories remain independent. Never edit a released SQLite baseline to upgrade existing databases; append versions and verify data preservation. A change landing after M097 must be accounted for explicitly before the baseline ships.
